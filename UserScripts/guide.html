Write your own car firmware

Real C, compiled into a real DLL, driving a real car in the game — without ever opening a terminal.

Every car in Tiny Torque can be driven by a piece of C code instead of by you. That code is firmware: it reads the car's sensors a hundred times a second and decides how much voltage to send the motors, how far to turn the wheels, when to brake. This folder is where you write it.

You edit a text file. You press a button in the game. A few seconds later the car is driving on your new code — the same car, in the same place, mid-race if you like. Nothing restarts. That loop is the whole point, and everything below is in service of it.

1. The five-minute version

  1. Start the game. Single Player → Simulate Controller.
  2. Press Build & Reload. The compiler output scrolls past in the pane below it. The first build takes longer than the rest — it is setting up as well as compiling.
  3. Press Run controller ▶. You are on track, and MyController.dll is driving. Hold the throttle; your code decides how to deliver it.
  4. Open MyController/my_controller.c in any text editor. Near the top is a block marked TUNING. Change SPEED_KP from 6.0f to 30.0f and save.
  5. Press Esc and hit Build & Reload again. The same panel is in the pause menu. The car lurches and hunts for its speed instead of settling on it — that is what too much proportional gain feels like, and you just felt it without leaving the track.
No compiler yet? The build pane will say so, and it prints the exact command to fix it: winget install --id BrechtSanders.WinLibs.POSIX.UCRT --exact. That one package brings a 64-bit C compiler, CMake and Ninja. Visual Studio's C++ workload works too, and is preferred automatically if you already have it.

2. What is in this folder

Tiny_Torque/ ├── UserScripts/ ← you are here │ ├── guide.html this page │ ├── lib/ │ │ └── tt_controller.h helper library — shared by every script below │ ├── MyController/ one folder = one controller = one DLL │ │ └── my_controller.c EDIT THIS — a working controller, speed loop and all │ └── user_sim_skeleton/ or start from nothing │ └── user_sim_skeleton.c plumbing only: one voltage to change │ ├── Controllers/ the game's own firmware, and the build system │ ├── hal/controller_api.h the actual contract. Worth reading. │ ├── car_pid/, car_sensors/, opus_mission/ worked examples │ └── build.ps1, CMakeLists.txt │ └── UnitySim/Assets/Plugins/x86_64/ where built DLLs land

The rule that makes this work: one folder under UserScripts/ becomes one DLL, named after the folder. MyController/ compiles to MyController.dll, which shows up in the game's Controller picker under exactly that name. Every .c file in the folder is compiled and linked together, so you can split a large controller across several files if you want to.

There is no list to add yourself to. The build system globs the folders, so a new folder is a new controller and a deleted folder is gone — you never edit a build file.

Folder names: letters, digits and underscores only. The name has to survive being a build target and a Windows file name at once, so My Controller and v2.0 are skipped — silently by the game's picker, with a message by the compiler. My_Controller and v2 are fine.

3. The edit → build → drive loop

The reason the game can swap a DLL it is currently running is that it never opens the one the compiler writes. It copies it to a scratch folder and loads the copy, leaving the original free to be overwritten at any moment. When you press Build & Reload, the sequence is: compile → ctrl_shutdown() on the old code → load the new DLL → ctrl_init() → ctrl_configure() → carry on stepping.

Your controller's state is reset; the car's is not. Speed, position, damage, lap count all survive. That is deliberate: the value of a hot reload is watching the same corner respond to different code. If you would rather start clean, there is a Reset the car after a reload toggle in the build panel.

Rebuild when I save

The build panel has a Rebuild when I save a source file toggle. With it on, saving any .c or .h under UserScripts/ (or Controllers/) starts a build by itself, about ¾ of a second after you stop typing. Editors write a file two or three times per save and the delay collapses that into one build; it also means a half-finished edit is not compiled while you are still typing it.

4. The screen in the game

Two pickers, and they are linked on purpose. Controller chooses what will drive when you press Run; Build chooses what gets compiled. Changing the first moves the second to match, because "I built one controller and raced a different one" is a confusing half-hour that nobody needs to have.

YOUR SCRIPTS is the honesty line. It reads the folder and the built DLL and tells you which is newer, so you find out that you forgot to rebuild here, rather than by wondering why your change did nothing on track.

5. Anatomy of a controller

Five functions. The game looks each one up by name when it loads your DLL; there is no registration step and no header you have to implement.

FunctionCalledFor
ctrl_init(float hz)once at start, and on every reload Set up your state. hz is the control rate — 100 today. Return 0 for OK.
ctrl_configure(...)once, right after init The car's parts list arrives here. Optional in the ABI, but you want it — see §8.
ctrl_step(in, out)100 times a second Read in, write out. This is the controller.
ctrl_shutdown()at the end, and before every reload Free anything you allocated. Runs once per Build & Reload, so a leak here is a leak per build.
ctrl_get_debug_names()at load Comma-separated names for your debug[] channels, so the graphs are labelled.
ctrl_get_vehicle()before the car exists Genuinely optional. Which car to drive — see below. Leave it out and the menu decides.
All five must exist. A DLL missing one still compiles and still loads — the game just cannot find the function, so the car coasts with no explanation. The build pane checks your sources for the four required names before it compiles and warns you if one is missing, because this failure is otherwise completely silent.

Choosing the car

The sixth function is the odd one out: it runs before there is a car, and its answer is which car gets built.

CTRL_EXPORT int ctrl_get_vehicle(void) {
    return CTRL_VEHICLE_TT_COUPE;
}

The Simulate Controller screen then builds a TT Coupe and ignores its own Vehicle picker — and says so on the screen, right under that picker, so a car you did not choose is never a mystery. Useful when your gains were tuned against one particular machine and judging them on anything else would be unfair to both.

The numbers are listed in Controllers/hal/controller_api.h: CTRL_VEHICLE_MENU (the default — whatever the menu picked), CTRL_VEHICLE_STOCK, and one each for Real Twin 1/10, TT Coupe, TT Baja, TT Patrol, TT Rattletrap, TT Redline, TT Highwing, TT Autopia and Opus Vector.

Two things it cannot do. A car you designed and saved yourself has no number — it did not exist when your DLL was compiled, so pick those in the menu. And a car you have not unlocked is refused: the menu's pick stands and the console says why. Compiling a number is not a way around the picker's list.
It must answer from a constant. There is no car and no parts list at the moment this is called — that is the whole point of calling it then. Do not try to read anything. A Build & Reload mid-drive swaps the code driving the car and never the car itself, so this is not asked again.

6. What your code can see

FieldUnitsNotes

Who is actually driving

setpoint[] deserves a paragraph, because it decides what kind of program you are writing.

In a Simulate Controller session you still hold the throttle and steer. Those inputs do not reach the wheels — they arrive in setpoint[] as a request, and your code decides how to honour it. That makes the default skeleton a driver's aid: a speed governor, a traction control, a steering filter. It is the most immediately satisfying place to start, because you can feel every change.

To write an autopilot instead, ignore setpoint[] and decide from sensors alone. The game's own opus_mission controller does exactly that — it drives a fixed manoeuvre by dead reckoning with nobody touching the keyboard — and there is a worked camera-following example at the bottom of my_controller.c.

7. What your code can do

Motors are driven by voltage, not throttle. You write a signed voltage into that motor's slot; positive drives forward, negative reverses, and the game clamps it to what the motor will actually take. That limit is per motor and is in the parts list, which is why you have to be told it rather than assume it.

tt_drive_volts(&g_car, out, 12.0f);   /* 12 V to every drive motor      */
tt_drive(&g_car, out, 0.5f);          /* or: half of each motor's max    */
tt_steer(out, -0.3f);                 /* 30% left                        */
tt_brake(out, 1.0f);                  /* full friction brake             */

Brakes and motors are independent. You can hold both at once; the car will do what a real one does, which is get hot and go nowhere.

8. Sensors and the parts list

Cars in this game are assembled from parts. How many motors there are, which slot each one answers to, how many volts it takes, what sensors are bolted where — all of it varies from car to car and can be changed in the garage between two runs of the same code.

So the game tells you, once, through ctrl_configure:

CTRL_EXPORT void ctrl_configure(const SensorInfo* sensors, int count) {
    tt_car_configure(&g_car, sensors, count);   /* copies what it needs */
}

Each SensorInfo carries a name (the one you typed in the garage), a type, and where that sensor's numbers live inside the flat sensor_data array. The helper does the lookups:

float d = tt_tof(&g_car, in, "tof_front", -1.0f);
if (d >= 0.0f && d < 6.0f) tt_brake(out, 1.0f - d / 6.0f);
SensorPublishesNotes
SENSOR_TOF[distance_m]Reports its configured max range when it sees nothing — not zero.
SENSOR_ENCODER[ang_vel, ticks]ticks wraps around. Take differences, not absolute values.
SENSOR_MOTOR[volts, amps, Nm]Its actuator_index is the slot you drive it with; range_max is its voltage limit.
SENSOR_IMU[gx gy gz ax ay az]Same numbers as gyro[]/accel[], for cars with more than one.
SENSOR_CAMERAno floatsThe frame arrives via cam_pixels.
SENSOR_SUSPENSION[force_N, compression, angle]Per strut. Compression near 1 means the corner is loaded.
SENSOR_BATTERY[volts, amps, soc]Pack level.
A car with none of these is legal. If your controller needs a front range-finder, check that it found one and behave sensibly when it did not. Every helper in tt_controller.h takes a fallback value for exactly this reason — a missing sensor should not read as "the road is clear".

9. The camera

A grayscale frame, one byte per pixel, row-major. Row 0 is the top of the image — y counts downward like a screen coordinate, so the road ahead is at large y and the sky is at small y.

int px = tt_cam_pixel(in, x, y);                    /* 0–255, 0 if off-frame  */
float lower = tt_cam_brightness(in, 0, 40, 63, 47); /* mean of a rectangle    */
float bias  = tt_cam_balance(in, 20);               /* −1 left … +1 right     */

tt_cam_balance compares the left and right halves of the bottom rows and is the shortest path to a car that follows something. Steer toward the bright side to follow a pale road across dark ground; negate it to follow a dark line across a pale floor.

Frames are slower than ticks. The camera updates at around 10 Hz while ctrl_step runs at 100, so the same frame is handed to you ten times over. Do not treat consecutive frames as consecutive moments in time.

Keeping frames: TtCamera

Everything above reads the live frame. in->cam_pixels is the game's own buffer, handed to you by pointer, and it is dead the instant ctrl_step returns — keeping that pointer is a use-after-free that will not announce itself. That is fine for "which side is brighter". It is no good for comparing this frame with the last one, or scanning an image across several ticks, or holding a picture of the moment something went wrong.

TtCamera is your own storage on your side of the boundary, holding the last few frames as plain 2D arrays:

static TtCamera g_cam;                       /* ~48 KB of static memory */

CTRL_EXPORT int ctrl_init(float hz) { tt_cam_init(&g_cam); return 0; }

CTRL_EXPORT void ctrl_step(const CtrlInputs* in, CtrlOutputs* out) {
    memset(out, 0, sizeof(*out));

    if (tt_cam_update(&g_cam, in)) {         /* true only on a NEW frame */
        const TtFrame* f = tt_cam_newest(&g_cam);
        int p = f->px[10][32];               /* row 10 from the TOP, column 32 */

        const TtFrame* prev = tt_cam_frame(&g_cam, 1);   /* NULL until there is one */
        if (prev) { /* ...what moved between the two... */ }
    }
}

The if is the point. Since the ABI carries no frame counter, tt_cam_update works out whether the picture is new by comparing the bytes, and returns 1 only when it changed. Put your image processing behind that test and it runs ten times a second instead of a hundred.

f->px[y][x] is the picture, row 0 at the top, same as the live buffer. The block is a fixed 128×96 whatever the camera's real size — so the indexing needs no arithmetic — and f->width/f->height say how much of it is the image. The padding beyond that is black and stays black. Use tt_frame_px(f, x, y) when x and y come from a calculation rather than from a loop whose bounds you wrote yourself.

Two identical captures look like one. The history is of distinct frames, not of captures. Park facing a blank wall and f->seq stops advancing, because nothing about the picture is new — which is the right answer for a controller that reacts to what it sees. If you need to know the camera is still alive, watch in->time_s. And tt_cam_age(&g_cam, in) will tell you how stale the newest frame is: at 10 Hz it swings between 0 and 0.1 s, so a car steering from an image is steering from something up to a tenth of a second out of date. That is the camera, not the buffering, and a real one does the same.
Memory. One kept frame is 12 KB; the default four is about 48 KB of static. #define TT_CAM_FRAMES before including the header to keep more or fewer — 1 is legal and means "the current frame only", in which case tt_cam_frame(c, 1) is always NULL. There is no malloc anywhere in it: the DLL is torn down and rebuilt on every Build & Reload, and a buffer that has to be freed is a leak per build waiting to be forgotten.

10. The helper library

lib/tt_controller.h is header-only — #include "tt_controller.h" and there is nothing to link. Everything in it is a thin wrapper over fields that are already in the structs, so you can ignore it entirely and write against controller_api.h directly. Several of the game's own controllers do.

tt_lerp / tt_deadzoneBlend between two values; zero out small ones.
tt_pid_init / _limits / _update / _resetPID with a clamped integrator and derivative-on-measurement — no wind-up, no kick when the target jumps.
tt_car_configureUnpack the parts list. Call from ctrl_configure.
tt_sensor_index / _of_type / _valueFind a sensor by name or type; read one of its numbers with a fallback.

You may also #include "pid.h" — the game's own PID, which its shipped controllers use. It is on the include path already.

11. Graphs and telemetry

out->debug[16] is sixteen free channels. Whatever you put in them is graphed live in the game and written to the telemetry CSV. Name them and they are labelled:

enum { DBG_TARGET = 0, DBG_SPEED, DBG_VOLTS, DBG_COUNT };

CTRL_EXPORT const char* ctrl_get_debug_names(void) {
    return "target,speed,volts";      /* same order as the enum */
}
...
out->debug[DBG_SPEED] = speed;

This is the fastest debugging tool you have. There is no printf to a console here, no breakpoint to set — but you can put any intermediate value on a graph and watch it against what the car did. Plot the thing you think is wrong.

12. Making a second controller

  1. Copy the whole MyController folder.
  2. Rename the copy — letters, digits and underscores. LineFollower.
  3. That is the entire procedure. LineFollower is now in the Build picker and LineFollower.dll in the Controller picker after you build it.

The two are completely independent: separate DLLs, separate state, separate everything. Keeping a version that works while you break a copy of it is the point.

Both see lib/tt_controller.h, so a change there changes all of them — which is either exactly what you want or a nasty surprise, depending on why you edited it.

13. When it goes wrong

What you seeWhat it is
Red compiler errors in the pane Normal C errors, with file and line. The old DLL keeps driving — a failed build never replaces a working controller.
no 64-bit C compiler found Nothing to compile with. Run the winget command in the message; a 32-bit gcc is rejected on purpose, since the game cannot load a 32-bit DLL.
Build succeeds, car does nothing Usually a missing export. The pane names which one. Check for a typo in ctrl_step.
reload failed — running open-loop The DLL built but would not load. Almost always a missing dependency; the build already links the runtime statically to prevent it, so this is worth reporting.
note: built 'X', but this car runs 'Y' Exactly what it says. You compiled a different controller from the one driving.
EDITED SINCE THE LAST BUILD You saved and did not rebuild. The DLL is older than your source.
Nothing happens when you press Build The pane will name the reason — no Controllers folder found, or no .c file in the script folder. There is a path box for the first case.
Car drives, but ignores your changes Check the Controller picker is on your DLL and not one of the four shipped ones.

14. The one real danger

A bad pointer in your C code crashes the whole process. Not your controller — the process. In the Unity editor that means the editor, with whatever you had unsaved in it. There is no sandbox around a native DLL, and no try/catch anywhere in the game can catch an access violation.

This is not a reason to be timid; it is a reason to check your indices. Every helper in tt_controller.h bounds-checks and returns a fallback rather than reading past the end of an array, and that is why. If you index sensor_data or cam_pixels by hand, do the same.

The game flushes telemetry to disk before every panel-triggered build, so a crash costs you the session but not the data.

One more, much smaller: if the crash log names a DLL in your temp folder that does not exist, that is expected. The game loads a scratch copy of your DLL so the compiler can overwrite the original, and deletes the copy on unload.
